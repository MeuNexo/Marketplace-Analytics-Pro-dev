<objective>
Construir a ingestão das SAÍDAS de caixa via integração Tiny ERP (CASH-02 atualizada, Wesley
2026-06-18): a Edge Function `sync-tiny-payables` que lê as contas a pagar do Tiny (`/contas-pagar`)
por loja (ml_user_id) e grava em `cash_outflows` com `source='tiny'`, mais o pg_cron a cada 6h que a
dispara. A tabela `cash_outflows` (com schema Tiny) é criada no plano 49-01; este plano só adiciona a
EF + cron + registro no config.toml.

Purpose: A decisão CASH-02 mudou — as saídas NÃO são mais lançamento manual. Vêm do Tiny já na Wave 1.
Sem esta EF, `cash_outflows` ficaria vazia e o RPC `get_cashflow` (Wave 2) calcularia o saldo só com
entradas — caixa errado (sem despesas reais).

Output: 1 Edge Function (saídas Tiny), 1 entrada de pg_cron (Pattern B, 6h), 1 bloco no config.toml.

Este plano roda na MESMA Wave 1 que o 49-01, mas DEPENDE dele: a migration da tabela `cash_outflows`
está no 49-01 (compartilhada). Não há sobreposição de arquivos entre 49-01 e 49-05 (este só cria a EF
e o cron de saídas) — por isso podem ser planejados em paralelo, com 49-05 deployado após a tabela existir.

    FETCH (subseção 1 e 6 do RESEARCH): GET /contas-pagar com params dataVencimentoInicial=hoje-90d, dataVencimentoFinal=hoje+90d,
    pagina=N, limit=100. CRÍTICO: NÃO enviar o parâmetro `situacao` à API (Tiny v3 rejeita/ignora o enum — armadilha A5); filtrar/normalizar
    situação client-side. Paginação: incrementar `pagina` enquanto itens.length === 100, com sleep ~600ms entre páginas (rate limit Tiny).
    MAPEAMENTO por item (subseção 2 do RESEARCH): id → tiny_payable_id; valor → amount; dataVencimento[:10] → outflow_date (DATE,
    string YYYY-MM-DD, sem conversão de timezone); historico/descricao → description; contato.nome/nomeFornecedor → supplier;
    tipo → category; numeroDocumento → document_number; situacao normalizada → status. NORMALIZAÇÃO de situação client-side:
    "pago"/"quitado"/"2" → 'paid'; o resto (em_aberto/aberto/pendente/1) → 'pending'. source = 'tiny' em todos os registros.
    DATA DA SAÍDA: usar dataVencimento[:10] como outflow_date (premissa A7: a API /contas-pagar pode não retornar dataPagamento;

    chamada Tiny e a contagem de itens por loja (smoke — premissa A3: a org precisa ter contas a pagar cadastradas no Tiny).
    config.toml: adicionar bloco [functions.sync-tiny-payables] com verify_jwt = false (igual sync-tiny-costs — chamada por cron/service role).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pg_cron → Edge Function | cron autentica via service_role_key do vault |
| Edge Function → API Tiny ERP | token OAuth Tiny de ml_tokens (refresh via tiny-oauth) |
| Edge Function (service role) → cash_outflows | service role ignora RLS; escrita só pela EF |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-49-05-01 | Spoofing | EF sync-tiny-payables | mitigate | requireServiceRole (Bearer == SERVICE_KEY); verify_jwt=false só porque o guard é o service role check |
| T-49-05-02 | Tampering | cron → EF | mitigate | Pattern B: Authorization derivado de vault.decrypted_secrets (segredo não hardcoded na migration) |
| T-49-05-03 | Information Disclosure | cash_outflows entre orgs | mitigate | upsert grava organization_id da linha de ml_tokens; RLS org-first de cash_outflows (criada no 49-01) protege leitura |
| T-49-05-04 | Tampering | dados duplicados em re-sync | mitigate | UNIQUE (organization_id, tiny_payable_id) + upsert ignoreDuplicates:false (idempotente, atualiza status) |
| T-49-05-05 | Information Disclosure | token Tiny reusado/exposto | accept | token já armazenado em ml_tokens; mesmo padrão de sync-tiny-costs em produção há meses |
</threat_model>
