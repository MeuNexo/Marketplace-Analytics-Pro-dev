Usar SUPABASE_SERVICE_ROLE_KEY para o client, igual às irmãs.

    Validação server-side do arquivo (autoridade — SEND-ATT-01), ANTES de subir ao ML: definir inline (Deno não importa `src/lib`) as constantes espelhadas do Plano 02 — `ALLOWED_UPLOAD_TYPES` = ["image/jpeg","image/png","application/pdf"], `MAX_UPLOAD_BYTES` = 5*1024*1024, `FILENAME_MAX_CHARS` = 125, `FILENAME_SAFE_RE` = /^[a-zA-Z0-9_.-]+$/. Rejeitar (400, mensagem PT-BR clara) se: `file.type` ∉ ALLOWED_UPLOAD_TYPES; `file.size` > MAX_UPLOAD_BYTES; nome de arquivo (do `file.name` quando presente) com comprimento > FILENAME_MAX_CHARS ou não-casando FILENAME_SAFE_RE. Manter um comentário curto de que estes limites espelham exatamente `src/lib/attachmentUploadValidation.ts` (Plano 02).

    Só DEPOIS do gate + validação: montar um novo `FormData` e anexar o Blob no campo `file` usando a forma de 3 argumentos `formData.append("file", blob, filename)` — passar explicitamente o filename (do `file.name` recebido) para que o ML receba o nome real e não "blob" (importante para a regra de nome ≤125/safe-chars do ML). Depois `POST` para `${ML_API}/post-purchase/v1/claims/${claim_id}/attachments` com header `Authorization: "Bearer " + access_token` e `api-version: "2"` (NÃO setar Content-Type manualmente — o runtime injeta o boundary do multipart). Ler a resposta JSON `{ user_id, filename }`; devolver `{ ok: true, filename }`. Envolver tudo num try/catch que responde 500 "Internal server error" sem vazar detalhes.
