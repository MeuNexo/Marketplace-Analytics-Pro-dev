<objective>
Corrigir a edge function sync-tiny-costs para que a Fase 2 (busca de custo individual via /produtos/{id}) rode em background, priorize os SKUs ainda sem custo e use um cap maior com guarda de tempo — resolvendo o problema de os 29 SKUs faltantes nunca entrarem no ciclo por ficarem além da posição 80 da fila.

Com waitUntil + 202 imediato o sync roda por até 150s (free tier) em background. A priorização garante que os 29 SKUs faltantes sejam os primeiros na fila, e o cap elevado (250 vs 80 anterior) com guarda de 120s cobre a totalidade mesmo com RATE_MS=1100ms por chamada.

Reescreva `supabase/functions/sync-tiny-costs/index.ts` preservando TODOS os helpers existentes sem alteração — `sleep`, `json`, `corsHeaders`, `sb`, `getTinyToken`, `tinyGet`, `fetchAllProducts`, a interface `ProductEntry` — e aplicando as quatro mudanças abaixo:

**A. Declaração de tipo EdgeRuntime (após os imports, antes dos const)**
Adicionar: `declare const EdgeRuntime: { waitUntil: (p: Promise<unknown>) => void }`
EdgeRuntime é global no runtime Supabase Edge; a declaração apenas satisfaz o deno check sem import algum. Idêntico à linha 31 do arquivo sync-tiny-payables.

**B. Novas constantes (junto a RATE_MS / BATCH_SIZE)**
Adicionar `CAP_DETAIL = 250` e `PHASE2_TIMEOUT_MS = 120_000`. O número 80 hardcoded na linha 207 do original será substituído por CAP_DETAIL dentro de runSync. Não remover RATE_MS nem BATCH_SIZE.

**C. Nova função `runSync` (imediatamente antes de `serve`)**
Assinatura: `async function runSync(mlUserId: string, userId: string | null): Promise<void>`
Toda a função deve estar envolta em um try/catch externo que loga `console.error('[sync-tiny-costs] runSync ERRO não capturado:', message)` em caso de exceção inesperada — equivalente ao "Pitfall 4" documentado em sync-tiny-payables.

Corpo de runSync (ordem de execução):

1. Derivar `scopeUserId`: fazer a mesma query em `ml_tokens` que o código original faz em serve() — selecionar `user_id` onde `ml_user_id = mlUserId`. Resolver `scopeUserId = userId ?? (tokenRow?.user_id ?? null)`. Se `scopeUserId` for null, logar e retornar cedo (sem throw).

2. Chamar `getTinyToken(mlUserId)`. Chamar `fetchAllProducts(tinyToken)`. Se `allProducts.length === 0`, logar e retornar.

3. Separar `withPrice` e `withoutPrice` com os mesmos filtros do original (`p.cost > 0`). Definir `syncAt = new Date().toISOString()`.

4. **Fase 1 — idêntica ao original**: loop `for (let i = 0; i < withPrice.length; i += BATCH_SIZE)`, mapear rows com campos `{ user_id: scopeUserId, item_id: 'TINY_' + p.sku, seller_sku: p.sku, cost: p.cost, updated_at: syncAt }`, upsert com `onConflict: 'user_id,seller_sku', ignoreDuplicates: false`. Contadores `synced` e `errors` locais.

5. **Priorização de faltantes (COSTS-02)**: antes de entrar no loop de Fase 2, consultar `sb.from('ml_product_costs').select('seller_sku').eq('user_id', scopeUserId)` para obter os SKUs já existentes. Construir `existingSkus = new Set<string>` com os valores retornados. Ordenar `withoutPrice` in-place com comparador `(a, b) => (existingSkus.has(a.sku) ? 1 : 0) - (existingSkus.has(b.sku) ? 1 : 0)` — entradas ausentes (not in set) ficam na frente. Se a query falhar, logar o aviso e continuar com a ordem original (não abortar).

6. **Fase 2 — cap elevado + guarda de tempo (COSTS-03)**: `const detailQueue = withoutPrice.slice(0, CAP_DETAIL)`. Registrar `const t0 = Date.now()` antes do loop externo. No topo de cada iteração do loop de batches (antes de processar o batch), verificar `if (Date.now() - t0 > PHASE2_TIMEOUT_MS)` e, se verdadeiro, logar `'[sync-tiny-costs] Phase 2 time guard triggered'` e executar `break`. Todo o restante do loop interno (a iteração por produto, o `tinyGet`, o sleep com RATE_MS, a construção de rows e o upsert) é idêntico ao original.

7. Ao final, logar um resumo: `synced`, `errors`, `phase2Processed`, `phase2Skipped` (= `withoutPrice.length - detailQueue.length`).

**D. Reescrever `serve()` mantendo a auth inline e delegando tudo mais para runSync**
Manter exatamente:
- Handler OPTIONS.
- Bloco de extração do `jwt` do header Authorization.
- Bloco de `sb.auth.getUser(jwt)` para derivar `userId` (quando o token não é a service-role key).
- Guard `if (!userId && jwt !== SERVICE_KEY) return json({ error: "Unauthorized" }, 401)`.
- Parse de `body` com try/catch interno.
- Parse de `mlUserId = body.ml_user_id` e guard `if (!mlUserId) return json({ error: "ml_user_id obrigatório" }, 400)`.

Remover de `serve()`: a query a `ml_tokens` para `tokenRow`/`scopeUserId`, a chamada a `getTinyToken`, `fetchAllProducts`, os loops de Fase 1 e Fase 2, o cálculo de `skippedDetail` e o `return json({ok:true, synced, ...})` final.

Após validar `mlUserId`, substituir tudo isso por:
`EdgeRuntime.waitUntil(runSync(mlUserId, userId));`
`return json({ ok: true, msg: "sync enqueued" }, 202);`

O try/catch externo em `serve()` continua cobrindo eventuais erros no bloco de auth inline e retorna 500 se necessário.

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-64-01 | Spoofing | serve() auth guard | mitigate | Auth inline permanece antes do waitUntil; service-role key OU getUser(jwt) validados antes de 202 ser retornado — não movido para background |
