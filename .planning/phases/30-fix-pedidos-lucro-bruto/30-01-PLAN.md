### Task 30-01-C: Fix Bug 1 — useMLCostWaterfall retorna null quando sem dados reais

**Arquivo:** `src/hooks/useMLCostWaterfall.ts`

**Problema:** Quando `paid_revenue = 0` mas `total_comissao > 0`, o hook retorna dados parciais que causam mistura de fontes no MLCostCard.

**Fix:** Se `paid_revenue = 0`, retornar `null` (sinaliza "sem dados reais — usar fallback de estimativas").

```typescript
// Depois de calcular os valores:
if (paid_revenue === 0) return null;  // sem pedidos pagos no período — caller usa fallback

return {
  paid_revenue,
  cancelled_revenue: 0,
  total_comissao,
  total_frete,
  cmv: Math.round(cmv * 100) / 100,
  has_cmv: cmv > 0,
  total_tax: Math.round(total_tax * 100) / 100,
  has_tax_data: total_tax > 0,
  revenue_per_store: new Map(),
};
```

**Resultado:** Quando `costWaterfall = null`, `MLCostCard` usa apenas `ml_daily_cache` para receita E estimativas hardcoded (11%/5%) para custos. Fonte consistente.

### Task 30-01-D: Fix Bug 2a — Query de pedidos com cast de data correto

**Arquivo:** `src/pages/mercadolivre/MLPedidos.tsx`

**Problema:** `.lte("data_pedido", dateTo)` compara `timestamptz` contra string de data sem considerar timezone. Pedidos do fim do dia BRT podem ser excluídos.

**Fix:** Adicionar 1 dia ao `dateTo` na query para cobrir o dia completo em BRT:

```typescript
// No loadOrders (linha ~716):
const queryDateTo = (() => {
  const d = new Date(dateTo + "T00:00:00Z");
  d.setUTCDate(d.getUTCDate() + 1);
  return d.toISOString().substring(0, 10);
})();

const { data, error } = await supabase
  .from("orders")
  .select(...)
  .in("ml_user_id", resolvedMLUserIds)
  .gte("data_pedido", dateFrom)
  .lte("data_pedido", queryDateTo)   // dateTo + 1 dia para cobrir BRT
  .order("data_pedido", { ascending: false })
  .range(from, from + PAGE - 1);
```

**Alternativa mais robusta:** Filtrar por `data_pedido::date` usando `.filter("data_pedido::date", "gte", dateFrom)` se o PostgREST suportar.

### Task 30-01-E: Fix Bug 2b — data_pedido armazenado em BRT

**Arquivo:** `supabase/functions/sync-ml-orders/index.ts`

**Problema:** `datePedido = order.date_created.substring(0, 10)` usa a data UTC, mas o range de busca usa BRT. Pedidos das primeiras 3 horas UTC do dia seguinte são armazenados com a data errada.

**Fix:** Converter `date_created` para BRT antes de extrair a data:

```typescript
// Linha ~296 em expandOrder():
// ANTES:
const datePedido = (order.date_created || "").substring(0, 10) || null;

// DEPOIS (converter UTC para BRT = UTC-3):
const datePedido = order.date_created
  ? (() => {
      const utcMs = new Date(order.date_created).getTime();
      const brtMs = utcMs - 3 * 60 * 60 * 1000;  // UTC-3
      return new Date(brtMs).toISOString().substring(0, 10);
    })()
  : null;
```

**Nota:** Esta mudança afeta apenas pedidos novos. Pedidos antigos já armazenados mantêm a data UTC. Para consistência futura, o fix de query (Task D) cobre o gap.

**Deploy após fix:**
```bash

```
