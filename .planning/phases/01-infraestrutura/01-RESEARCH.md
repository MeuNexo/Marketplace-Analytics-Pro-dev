For `ml_tax_config`, the write policies must narrow to `= 'owner'` only (not the full write group), as specified in INFRA-01.
- **Critical: function argument order.** The TypeScript type definitions confirm `is_org_member(_org_id, _user_id)` and `get_org_role(_org_id, _user_id)` — `organization_id` is the FIRST argument, `auth.uid()` is the second. This is inverted from the intuitive reading. Every existing migration uses `public.is_org_member(auth.uid(), organization_id)` — note `auth.uid()` is first in SQL calls, which maps to `_user_id` despite the type signature showing `_org_id` first. **Verify the actual function call order from the working migrations:** the migrations always write `public.is_org_member(auth.uid(), organization_id)` meaning the first parameter is the user. The types.ts shows `Args: { _org_id: string; _user_id: string }` but this reflects named params, not positional order. Rely on the migration code pattern: `public.is_org_member(auth.uid(), organization_id)`.
- **Hook pattern:** The closest analog is `useMLProductCosts` (`src/hooks/useMLProductCosts.ts`) — uses `useState<Map<...>>` + `useCallback` + `useEffect`, NOT TanStack Query. However, INFRA-02 explicitly requires "padrão TanStack Query existente." The TanStack Query pattern is in `useMLQueries.ts`. The hook must use `useQuery` from `@tanstack/react-query`, not the legacy `useState/useCallback/useEffect` pattern.
- **TypeScript type regeneration:** There is NO npm script in `package.json` for `supabase gen types`. The types file `src/integrations/supabase/types.ts` header says "automatically generated — do not edit it directly" but no generation command exists in `package.json`. The planner must include a manual step: run `npx supabase gen types typescript --project-id gionpsuunfkkzzjdubfy > src/integrations/supabase/types.ts` OR hand-edit the types file to add the new table and enum shapes.
- **Schema decision:** ARCHITECTURE.md (in `.planning/research/`) is the authoritative schema. It specifies normalized columns (not JSONB), a PostgreSQL `tax_regime` enum, and `effective_rate` computed by trigger. STACK.md suggests JSONB — that recommendation is superseded by ARCHITECTURE.md, which was finalized after the stack research.

**Trigger pattern** — no existing trigger in this codebase to copy from. The pattern to use for `handle_updated_at` is referenced in `20260513174419` (REVOKE on it), so the function exists. For `effective_rate`, a new trigger function must be written from scratch:
```sql
CREATE OR REPLACE FUNCTION public.calculate_effective_rate()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.effective_rate := CASE NEW.regime
    WHEN 'simples_nacional' THEN
      COALESCE(NEW.sn_aliquota_efetiva, 0)
    WHEN 'lucro_presumido' THEN
      COALESCE(NEW.lp_pis, 0) + COALESCE(NEW.lp_cofins, 0)
      + COALESCE(NEW.lp_irpj, 0) + COALESCE(NEW.lp_csll, 0)
    WHEN 'lucro_real' THEN
      GREATEST(0,
        (COALESCE(NEW.lr_pis_debito, 0) + COALESCE(NEW.lr_cofins_debito, 0)
         + COALESCE(NEW.lr_icms_debito, 0))
        - (COALESCE(NEW.lr_pis_credito, 0) + COALESCE(NEW.lr_cofins_credito, 0)
           + COALESCE(NEW.lr_icms_credito, 0))
      )
    ELSE 0
  END;
  NEW.updated_at := now();
  RETURN NEW;
END;
$$;

CREATE TRIGGER ml_tax_config_effective_rate
  BEFORE INSERT OR UPDATE ON public.ml_tax_config
  FOR EACH ROW EXECUTE FUNCTION public.calculate_effective_rate();
```

Note: ARCHITECTURE.md specifies Lucro Real as `(debitos) - (creditos)` without GREATEST — the planner must decide whether to clamp to 0 or allow negative. The requirement says display clamps to 0% in Phase 2 (FISCAL-05), so the DB can store the raw computed value; GREATEST(0,...) in the trigger is optional.

## RLS Pattern

**Exact pattern from `20260423153544` (org-scope migration, verified):**

```sql
-- SELECT: all org members
CREATE POLICY "ml_tax_config select"
  ON public.ml_tax_config FOR SELECT TO authenticated
  USING (public.is_org_member(auth.uid(), organization_id));

-- INSERT: owner only
CREATE POLICY "ml_tax_config insert"
  ON public.ml_tax_config FOR INSERT TO authenticated
  WITH CHECK (public.get_org_role(auth.uid(), organization_id) = 'owner');

-- UPDATE: owner only
CREATE POLICY "ml_tax_config update"
  ON public.ml_tax_config FOR UPDATE TO authenticated
  USING (public.get_org_role(auth.uid(), organization_id) = 'owner');

-- DELETE: owner only
CREATE POLICY "ml_tax_config delete"
  ON public.ml_tax_config FOR DELETE TO authenticated
  USING (public.get_org_role(auth.uid(), organization_id) = 'owner');
```

**Key difference from other tables:** All other domain tables allow `IN ('owner','admin','member')` for writes. `ml_tax_config` is `= 'owner'` only, per INFRA-01.

**Important:** Do NOT use `organization_id IS NOT NULL AND ...` guard in the USING clause. `ml_tax_config` has `organization_id NOT NULL` by schema definition, so the guard is unnecessary — and unlike the legacy tables that added `organization_id` as nullable, this is a new table with NOT NULL from creation.

**Function argument order in SQL:** `public.is_org_member(auth.uid(), organization_id)` — user first, org second. Same for `get_org_role`.

## Hook Pattern

**Closest analog:** `useMLProductCosts` at `src/hooks/useMLProductCosts.ts`
- Uses `Map<string, ProductCost>` exactly
- Uses direct Supabase client (`import { supabase } from "@/integrations/supabase/client"`)
- Uses `useAuth()` for user context
- **BUT**: uses legacy `useState/useCallback/useEffect` pattern, NOT TanStack Query

**INFRA-02 requires TanStack Query.** The `useMLQueries.ts` file shows the TanStack Query pattern:

```typescript
// From useMLQueries.ts
import { useQuery, keepPreviousData } from "@tanstack/react-query";
import { useAuth } from "@/contexts/AuthContext";
import { useOrganization } from "@/contexts/OrganizationContext";
import { supabase } from "@/integrations/supabase/client";

export function useMLTaxConfig(mlUserIds: string[], orgId: string) {
  const { user } = useAuth();

  return useQuery({
    queryKey: ["ml", "taxConfig", orgId, mlUserIds] as const,
    queryFn: async (): Promise<Map<string, { regime: string; effective_rate: number }>> => {
      const { data, error } = await supabase
        .from("ml_tax_config")
        .select("ml_user_id, regime, effective_rate")
        .in("ml_user_id", mlUserIds)
        .eq("organization_id", orgId);
      if (error) throw error;
      const map = new Map<string, { regime: string; effective_rate: number }>();
      for (const row of data ?? []) {
        map.set(row.ml_user_id, {
          regime: row.regime,
          effective_rate: Number(row.effective_rate),
        });
      }
      return map;
    },
    enabled: !!user && mlUserIds.length > 0 && !!orgId,
    staleTime: 5 * 60 * 1000,
  });
}
```

**Query key pattern from `useMLQueries.ts`:** `["ml", type, userId, mlIds, ...]`

**Supabase client import:** `import { supabase } from "@/integrations/supabase/client";` — path alias `@/` maps to `src/`.

**Context imports:**
- `import { useAuth } from "@/contexts/AuthContext";` — provides `user`
- `import { useOrganization } from "@/contexts/OrganizationContext";` — provides `currentOrg`

## Implementation Notes

### Schema Decision: Normalized Columns vs JSONB

STACK.md recommended JSONB. ARCHITECTURE.md (the more recent, more authoritative document) specifies normalized columns. The planner must follow ARCHITECTURE.md. This means:
- 12 regime-specific columns (`sn_aliquota_efetiva`, `lp_pis`, `lp_cofins`, `lp_irpj`, `lp_csll`, `lr_pis_debito`, `lr_pis_credito`, `lr_cofins_debito`, `lr_cofins_credito`, `lr_icms_debito`, `lr_icms_credito`)
- All `numeric(6,4) DEFAULT NULL`
- Queryable via SQL, no JSONB extraction operators in hooks

### Lucro Real: Negative effective_rate

ARCHITECTURE.md formula: `(debitos) - (creditos)`. If credits exceed debits, result is negative. INFRA-01 does not specify clamping at the DB level. FISCAL-05 (Phase 2) says "limitar display a 0%". The planner should store the raw value (possibly negative) and let the UI clamp. If storing negative in `NUMERIC(6,4)` is a concern, the trigger can use `GREATEST(0, ...)`. This is a decision for the planner to make explicit.

### Hook Return Type

INFRA-02 specifies `Map<ml_user_id, { regime, effective_rate }>`. The regime value should be typed as `Database["public"]["Enums"]["tax_regime"]` after types are updated, or as `string` before types are available. Use a local interface to stay type-safe regardless of when the generated types are updated.

### TanStack Query staleTime

No existing hook queries config tables with infrequent changes. Tax config changes rarely — `staleTime: 5 * 60 * 1000` (5 minutes) is appropriate, matching the ads cache TTL used in `useMLAds`. The `useMLDailyQuery` uses 2 minutes; use a longer staleTime since tax config is write-infrequent.

### Query Key Stability

`mlUserIds: string[]` array in the query key will break referential equality between renders. The calling component must either memoize the array or the hook must sort+join it for the key. Pattern from `useMLQueries.ts`: arrays are passed directly into query keys — React Query does deep equality on arrays in query keys, so this is safe.

### RLS for SELECT by Non-Owners

The SELECT policy uses `is_org_member` (not `get_org_role = 'owner'`) intentionally — all org members need to read tax config to populate the Impostos column in MLProdutos. This is documented in ARCHITECTURE.md.

### Migration Filename

The most recent dated migration is `20260514130000_fix_ml_product_daily_cache_unique.sql`. Use `20260515120000_ml_tax_config.sql` to sort after it. Alternatively, use today's datetime: `20260515120000_ml_tax_config.sql`.

### No Edge Function

This phase requires no edge function. Direct Supabase client query is sufficient — confirmed by ARCHITECTURE.md ("Sem edge function").
