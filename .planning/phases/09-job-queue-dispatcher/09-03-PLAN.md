<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 2: Validar SYNC-03 — watchdog de retry com backoff e cap de 3 tentativas</name>
  <what-built>
    A migration criou o agendamento pg_cron 'sync-job-retry-watchdog' que reinsere jobs failed com retries < 3 apos o backoff correspondente. Precisamos validar tanto a reinserção quanto o cap de 3 tentativas.
  </what-built>
  <how-to-verify>
    Execute no SQL Editor (https://supabase.com/dashboard/project/gionpsuunfkkzzjdubfy/sql):

    CENARIO A — Job failed com retries=0 reinserido apos 5 min:

    PASSO A1 — Inserir job failed simulando backoff vencido (finished_at ha 6 minutos):
    INSERT INTO public.sync_jobs (organization_id, ml_user_id, job_type, status, retries, finished_at)
    VALUES (
      (SELECT id FROM public.organizations LIMIT 1),
      'WATCHDOG_TEST_USER',
      'orders',
      'failed',
      0,
      now() - interval '6 minutes'
    )
    RETURNING id;
    (Anotar o id como {test_job_id})

    PASSO A2 — Executar o SQL do watchdog manualmente (mesma logica do pg_cron):
    INSERT INTO public.sync_jobs (organization_id, ml_user_id, job_type, status, retries, date_from, date_to)
    SELECT organization_id, ml_user_id, job_type, 'pending', retries + 1, date_from, date_to
    FROM public.sync_jobs
    WHERE status = 'failed'
      AND retries < 3
      AND finished_at + (
        CASE retries
          WHEN 0 THEN interval '5 minutes'
          WHEN 1 THEN interval '15 minutes'
          WHEN 2 THEN interval '30 minutes'
          ELSE interval '999 hours'
        END
      ) <= now()
      AND NOT EXISTS (
        SELECT 1 FROM public.sync_jobs j2
        WHERE j2.organization_id = sync_jobs.organization_id
          AND j2.ml_user_id = sync_jobs.ml_user_id
          AND j2.job_type = sync_jobs.job_type
          AND j2.status IN ('pending', 'running')
      );
    ESPERADO: "INSERT 1" ou mais (o job de teste deve ter sido reinserido)

    PASSO A3 — Confirmar reinserção:
    SELECT id, status, retries, created_at
    FROM public.sync_jobs
    WHERE ml_user_id = 'WATCHDOG_TEST_USER'
    ORDER BY created_at DESC;
    ESPERADO: dois registros — o original (status='failed', retries=0) e o novo (status='pending', retries=1)

    CENARIO B — Job failed com retries=3 NAO reinserido:

    PASSO B1 — Inserir job failed com retries=3:
    INSERT INTO public.sync_jobs (organization_id, ml_user_id, job_type, status, retries, finished_at)
    VALUES (
      (SELECT id FROM public.organizations LIMIT 1),
      'WATCHDOG_TEST_CAP',
      'orders',
      'failed',
      3,
      now() - interval '60 minutes'
    )
    RETURNING id;

    PASSO B2 — Executar o SQL do watchdog manualmente (mesmo SQL do PASSO A2)
    ESPERADO: "INSERT 0" (nenhum job com retries=3 deve ser reinserido)

    PASSO B3 — Confirmar que job permanece failed:
    SELECT id, status, retries
    FROM public.sync_jobs
    WHERE ml_user_id = 'WATCHDOG_TEST_CAP';
    ESPERADO: 1 registro com status='failed' e retries=3 — sem novo job pending

    LIMPEZA (opcional, recomendado):
    DELETE FROM public.sync_jobs WHERE ml_user_id IN ('WATCHDOG_TEST_USER', 'WATCHDOG_TEST_CAP');
  </how-to-verify>
  <acceptance_criteria>
    - Cenario A: job failed com retries=0 e finished_at ha 6 minutos e reinserido como pending com retries=1
    - Cenario A: o SQL do watchdog retorna "INSERT 1" (ou mais se existirem outros jobs elegíveis)
    - Cenario B: job failed com retries=3 NAO e reinserido — SQL do watchdog retorna "INSERT 0" para esse job

  </acceptance_criteria>
  <resume-signal>Digite "aprovado" se ambos os cenarios foram validados (retry com retries=0 reinseriu, retries=3 NAO reinseriu), ou descreva qual cenario falhou e o resultado obtido.</resume-signal>
