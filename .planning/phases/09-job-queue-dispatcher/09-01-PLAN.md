    SECAO Function — claim_next_sync_job() (claim atomico com FOR UPDATE SKIP LOCKED):
    Esta funcao e necessaria porque supabase-js v2 nao expoe FOR UPDATE SKIP LOCKED diretamente;
    encapsulando em uma funcao SQL SECURITY DEFINER chamada via sb.rpc() o claim atomico fica
    disponivel para a edge function sem depender de query SQL raw.

    CREATE OR REPLACE FUNCTION public.claim_next_sync_job()
    RETURNS public.sync_jobs
    LANGUAGE plpgsql
    SECURITY DEFINER
    AS $$
    DECLARE
      v_job public.sync_jobs;
    BEGIN
      UPDATE public.sync_jobs
      SET status = 'running', started_at = now()
      WHERE id = (
        SELECT id
        FROM public.sync_jobs
        WHERE status = 'pending'
        ORDER BY created_at ASC
        LIMIT 1
        FOR UPDATE SKIP LOCKED
      )
      RETURNING * INTO v_job;

      RETURN v_job;
    END;
    $$;

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pg_cron → process-sync-job | pg_cron invoca a edge function via net.http_post com anon key + X-Cron-Secret; a funcao valida o service role key |
| process-sync-job → sync-ml-orders | Invocacao interna server-to-server com service role key no header Authorization |
| authenticated → sync_jobs | Usuarios autenticados podem ler jobs da propria org via RLS; nenhuma escrita direta |
| service_role → sync_jobs | dispatch_sync_jobs() e watchdog pg_cron escrevem jobs diretamente (SECURITY DEFINER / service_role) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Spoofing | process-sync-job auth | mitigate | requireCronOrServiceRole valida X-Cron-Secret (pg_cron automatico via vault) OU "Authorization: Bearer {SERVICE_ROLE_KEY}" (invocacoes manuais); retorna 401 se nenhum bater |
| T-09-02 | Tampering | sync_jobs INSERT via authenticated | mitigate | RLS sem policies INSERT/UPDATE/DELETE para authenticated; apenas service_role e funcoes SECURITY DEFINER escrevem |
| T-09-03 | Denial of Service | job duplicado via dispatch_sync_jobs() | mitigate | Guard SYNC-07: EXISTS check em status IN ('pending', 'running') antes de cada INSERT; funcao e idempotente |
| T-09-04 | Denial of Service | retry loop infinito em jobs failed | mitigate | Watchdog SYNC-03 so reinsere se retries < 3; jobs com retries >= 3 ficam em status 'failed' permanentemente |
| T-09-05 | Elevation of Privilege | dispatch_sync_jobs() SECURITY DEFINER | accept | Funcao executada no contexto do postgres superuser por design (necessario para acessar ml_tokens e organization_plans); sem parametros de entrada expostos a usuarios |
| T-09-06 | Information Disclosure | error_msg em sync_jobs | accept | Campo error_msg e visivel apenas para membros da org via RLS SELECT; nao exposto publicamente |
| T-09-07 | Repudiation | pg_cron fire-and-forget | accept | net.http_post e assincrono; resultados sao rastreados no status do job (completed/failed) com finished_at; auditoria via sync_jobs |
