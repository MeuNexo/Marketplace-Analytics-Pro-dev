# Quick 260627-1z0: Fix Parâmetro Reposição — Alvo Order-Up-To

**One-liner:** Migration corrige alvo de reposição para GREATEST(meta_cobertura, lead_time+7)+safety, eliminando colapso de compra quando lead_time > meta_cobertura.

## O Que Foi Feito

Criada migration `20260668000300_get_replenishment_by_sku_alvo_order_up_to.sql`, cópia exata da `20260668000200` com duas mudanças cirúrgicas no CTE `calc`:

| Local | Antes | Depois |
|-------|-------|--------|
| `alvo_v` | `(b.meta_cobertura_dias + b.safety_days)` | `(GREATEST(b.meta_cobertura_dias, b.lead_time_dias + 7) + b.safety_days)` |
| `compra` ELSE | `(b.meta_cobertura_dias + b.safety_days)` | `(GREATEST(b.meta_cobertura_dias, b.lead_time_dias + 7) + b.safety_days)` |

O `ponto` continua `(b.lead_time_dias + b.safety_days)` — inalterado.

## Problema Corrigido

Quando `meta_cobertura_dias` (ex.: 45) < `lead_time_dias` (ex.: 70 Pralana, até 85 em outras), o alvo ficava abaixo do ponto. Resultado: estoque+a_caminho entre alvo e ponto disparava o gatilho, mas a compra colapsava no MOQ porque o quantitativo faltante era mínimo ou negativo.

Com `GREATEST`, alvo >= ponto é garantido estruturalmente para todos os SKUs.
