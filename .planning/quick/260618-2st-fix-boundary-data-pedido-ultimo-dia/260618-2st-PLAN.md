# Quick 260618-2st: Fix boundary de data_pedido (timestamptz) que derruba o último dia do range

<objective>
A coluna `public.orders.data_pedido` é `timestamptz`. Três hooks filtram via PostgREST com `.gte("data_pedido", from).lte("data_pedido", to)`, onde `from`/`to` são strings só-data (`yyyy-MM-dd`, = meia-noite). Como `data_pedido <= '2026-06-17'` compara timestamp com meia-noite, **todos os pedidos do dia `to` (que têm hora > 00:00) são excluídos** → o último dia do range some. No filtro "hoje" (range de 1 dia), o gráfico/dado fica completamente vazio.

**Provado em produção:** para 06-17, `.lte('2026-06-17')` retorna 0 pedidos; `< '2026-06-18'` (e `data_pedido::date = '2026-06-17'`) retornam 870. Os RPCs do projeto já usam `data_pedido::date BETWEEN p_from AND p_to`; o `MLPedidos.tsx` (linhas 714-738) já compensa com `queryDateTo = dateTo + 1 dia`. Estes 3 hooks não compensam.

Fix: criar helper testável `nextDayUTC(dateStr)` e trocar o upper bound de `.lte("data_pedido", to)` para `.lt("data_pedido", nextDayUTC(to))` nos 3 hooks. Equivale a `data_pedido::date <= to` (inclui o dia `to` inteiro). NÃO alterar `MLPedidos.tsx` (já funciona). NÃO alterar o fallback `ml_product_daily_cache` (usa coluna `date`, já correto).
</objective>
